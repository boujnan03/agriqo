## 1. Executive Summary

This is a **single-process Streamlit app** (no backend server, no REST API, no database) that lets a user click a point on a map, download 10 years (2016–2025) of **NASA POWER** daily weather for it, and compare **three hard-coded crop rotations** with a transparent rule-based score (Water / Soil / Climate, 0–100, user-weighted). It then renders charts and a French template-based explanation with a limitations section. The pipeline is real end to end for NASA POWER: the code makes live API calls, caches them, and falls back to a bundled *real* POWER response for Beni Mellal (not fabricated data).

What it is **not**: the planned SMAP, MODIS/VIIRS and SoilGrids sources, the FastAPI backend and the "income" priority do not exist in the code. **The single most important thing to know before demoing:** the "Soil health" score uses **no soil data at all**. It is computed only from the team's own crop table (family, legume flag, a -1/0/+1 "soil effect") and is identical at every location on Earth. With the default sliders it also drives the ranking: rotation B (cereal monoculture) loses purely on soil (20/100). The crop table itself is approximate and unvalidated (`needs_validation: true`). With default sliders at Beni Mellal the app also reports "too close to call" for the top two (82.6 vs 79.7), so be ready to explain that banner.

**What the code does with a POWER response**
- `parse_response` (`:78-94`): builds a daily DataFrame, converts `-999` (and anything ≤ fill value) to NaN, sets soil wetness outside [0,1] and rain < 0 to NaN.
- Cache: raw JSON saved to `data/cache/{lat:.2f}_{lon:.2f}_{start}_{end}.json`; coordinates rounded to 0.01°; **never expires**.
- `features.compute_features`: Oct–May seasons (labelled by end year) and calendar years are kept only if all months are present **and ≥ 90 % of days have non-missing rainfall** (`features.py:53-56`); heat days (Tmax > 35 °C), longest dry spell (rain < 1 mm, NaN breaks the run), CV of seasonal rainfall, monthly climatology.
- **Fetched but never used in scoring:** `T2M_MIN`, `RH2M`, `ALLSKY_SFC_SW_DWN` (only downloaded). `GWETTOP/GWETROOT` are displayed and quoted in the explanation but not scored. `T2M_MAX` abs-max (`t_max_abs`) is computed but unused.
- Result on the real Beni Mellal data: 0.0 % missing values, 9 complete seasons (2017–2025), mean Oct–May rain 364 mm (min 251, CV 0.22), 78 heat days/year but only 4.2 in Oct–May, mean longest dry spell 31.7 days.

**Credentials:** none required, none present. No keys, tokens or secrets in code or data (grep for `key|token|secret` found nothing relevant).

## 5. Scoring Logic — As Actually Implemented

Rule-based and transparent; no ML. `docs/scoring.md` matches `src/scoring.py` (I compared constants and formulas; they agree). It differs from the plan in the weights (user sliders, equal by default, not 0.5/0.3/0.2) and in the third criterion (Climate, not Income).

**Total** (`scoring.py:152-168`): `total = w_water·Water + w_soil·Soil + w_climate·Climate`. Sliders are 0–10 (default 5/5/5, `app.py:45-47`), normalised to sum 1 (`normalize_weights`, negatives → 0, all-zero → ⅓ each). If a sub-score is `None` (missing NASA inputs), it is dropped and the remaining weights are re-normalised (`weights_used`).

**Water** (`:79-96`) — per crop slot: `rain` = mean Oct–May rain (or mean annual rain if `season == "year"`); `deficit = max(0, water_need_mm − rain)`; `score = 100·(1 − deficit/need)`. Rotation = mean of slots. Irrigation need = mean deficit per season.

**Soil** (`:100-117`, constants `:20-24`) — **crop table only**:
`50 + 15·(#legume slots) + 10·(#distinct families − 1) − 10·(#consecutive same-family pairs, wrapping last→first) + 5·Σ soil_health_effect`, clamped 0–100.

**Climate** (`:121-148`, constants `:27-31`):
- `heat = min(1, heat_days_season/20)`; `heat_year = min(1, heat_days_year/80)` (perennials only)
- `dry = clip((dry_spell − 15)/(60 − 15), 0, 1)`; `var = min(1, season_rain_cv/0.5)`; `drought = 0.5·dry + 0.5·var`
- per crop: `100 − 50·heat·(5 − heat_tol)/4 − 50·drought·(5 − drought_tol)/4`; rotation = mean.

**Ranking / uncertainty** (`rank`, `:171-180`): sort by total; if best − second < `TOO_CLOSE_POINTS = 3.0`, `top_too_close = True`.

**Actual output at Beni Mellal (my run, cached POWER data):**

| Weights (water/soil/climate) | Order (total) | Too close? |
|---|---|---|
| 1/1/1 (= UI default 5/5/5) | C 82.6 · A 79.7 · B 63.0 | **Yes** (gap 2.9) |
| water only | C 90.6 · B 84.3 · A 74.6 | No |
| soil only | A 85.0 · C 70.0 · B 20.0 | No |
| climate only | C 87.1 · B 84.6 · A 79.6 | Yes |

At 32.50,-6.69 (other cached point, 320 mm/season) the default order is C 75.1 · A 71.5 · B 54.7.

**Behavioural observations (from reading + the run):**
- **Order within a rotation does not matter for water or climate**: each slot is scored against the same location-wide mean, then averaged. `tests/test_scoring.py::test_too_close_flag` uses W→L vs L→W and gets identical scores. So the tool effectively ranks *sets of crops/families*, not sequences. Only the soil repeat-penalty sees adjacency.
- The ranking at default weights is largely decided by the **non-NASA, location-independent soil rule**: B's NASA-based water (84.3) and climate (84.6) are competitive with A and C; its low total (63.0) comes from soil = 20.
- **Heat stress is almost inert** for the current rotations: Oct–May has only ~4 heat days (stress 0.21). The window ends 31 May, so late-spring/early-summer heat during grain filling and the May–July harvest of sugar beet/chickpea is outside the scoring window (inferred from `SEASON_MONTHS` vs the `harvest` fields in `crops.json`). The perennial `heat_year` branch (`:143`) is used only by alfalfa, which no rotation contains → **dead code path in the current data**.
- Water score assumes irrigation fills any gap and treats total rainfall as fully usable (no effective rain, ET₀, soil storage, efficiency, dam allocation). Acknowledged in the UI limits.
- `TOO_CLOSE_POINTS = 3`, `HEAT_DAYS_FULL_STRESS = 20`, `DRY_SPELL_*`, `CV_FULL_STRESS` and all bonuses/penalties are **unjustified constants** (no citation or calibration in code or docs).

**Hardcoded stand-ins for real data:** the entire crop table and rotation list (see §4). Nothing numeric is invented at runtime; `explain.py` formats only computed values, with a few exceptions noted in §9.

## 6. API / Backend Overview

**There is no HTTP API and no server-side component** beyond Streamlit itself. No FastAPI/Flask/routes. The "backend" is a Python call chain invoked inside the Streamlit script:

| "Endpoint" (Python function) | Purpose | Notes |
|---|---|---|
| `power_client.get_power_data(lat, lon, start, end, use_cache, offline)` | cache → API → fallback | Returns `PowerData(source ∈ {api, cache, fallback}, note)`. Never raises *if* the fallback file exists — except for a corrupt cache file (§9). |
| `features.compute_features(df)` | daily → `Features(summary, seasons, years, monthly)` | |
| `scoring.score_all(summary, w_water, w_soil, w_climate, crops=None, rotations=None)` | scores + ranking | Raises `KeyError` on unknown crop id (tested). |
| `explain.explain(...)` / `explain.limitations(...)` | French markdown | Only `TEXTS["fr"]` exists. |

- **Validation:** none on user input. Lat/lon come from a map click (floats) and are not checked against Morocco/Tadla or valid ranges. No free-text input exists, so injection surface is minimal.
- **Error handling:** one broad `except Exception` around the API call that routes to the fallback (`power_client.py:125`). No handling in `app.py` for exceptions elsewhere.
- **Logging:** none (`print` only in `__main__` smoke tests).
- **Tests (22, all passing, no network):**
  - `test_scoring.py` (7): hand-computed example matching `docs/scoring.md §5`, weight normalisation, missing-rain renormalisation, all-missing → None, too-close flag, unknown crop, real JSON files score within 0–100 *using a synthetic summary*.
  - `test_features.py` (5): dry-spell NaN rule, seasonal sums/labels, heat days, season dropped for missing data, partial season dropped.
  - `test_power_client.py` (6): −999 → NaN, out-of-range soil wetness, fallback on failure, cache hit, offline flag, bundled fallback parses.
  - `test_explain.py` (4): numbers come from scoring, survives missing water, language key parity, limitations content.
  - **Not covered:** `app.py` (zero UI tests), perennial (`season: "year"`) paths in scoring, `rank().close_pairs`, corrupt-cache handling, the full real-data → score chain, the `trend` sentence, explanation when `n_seasons == 0`.

## 9. Known Issues, TODOs, and Risks

No `TODO`/`FIXME`/commented-out code found. Observations, most important first:

1. **Soil score is not data-driven** (`scoring.py:100-117`) and the limitations text never says "no actual soil measurements are used" (only that crop parameters are unvalidated, `explain.py:111-114`). The label "Santé du sol" can be read as satellite/soil-based.
2. **Streamlit cache pins a transient fallback** — `load()` is `@st.cache_data` keyed on `(lat, lon, offline)` (`app.py:24-27`). If the API fails once for a point, the fallback result is cached for that key for the life of the server process; turning offline off and re-clicking the same point will not retry (inferred from the Streamlit caching contract; not run).
3. **Corrupt/partial cache file crashes the app** — the cache read at `power_client.py:116-117` is outside the `try`, and the cache write at `:123` is non-atomic. A killed write leaves invalid JSON, after which every load of that point raises.
4. **Slow-network risk in a live demo** — 90 s timeout, no retry, blocking the UI before the fallback kicks in (`power_client.py:59, 70`). Use the offline toggle (or pre-warm the cache) for demos.
5. **Fallback returns Beni Mellal for any clicked point** (`:131`). A warning banner is shown (`app.py:65-66`) and the limitations text uses the fallback coordinates, but the sidebar and map marker still show the clicked coordinates.
6. **Default view shows "too close to call"** (gap 2.9 < 3.0) — honest, but check it before a demo; the threshold is arbitrary.
7. **Trend sentence can mislead** — `explain.py:177-181` compares the last 3 seasons to the previous 6 and states e.g. a "−25 %" difference with no significance caveat (my run: 296 mm vs 398 mm), based on 9 seasons of 0.5°-scale reanalysis. It reads like a climate trend.
8. **Missing-data edge cases present misleadingly**: if water/climate are `None`, the total silently becomes soil-only and is still announced as "Meilleure rotation" (`scoring.py:159-166`, `app.py:100-102`). `weights_used` is never shown in the UI, which displays the user's weights instead. KPI cells would print `nan` if no season is complete (`app.py:109-114`). `scoring.py:126` `(s.get("heat_days_year") or 0)` does not catch NaN (NaN is truthy) and `min(1.0, nan)` returns 1.0, i.e. worst-case stress.
9. **Possible reset-button bug (unverified)** — `st_folium` returns `last_clicked` on every rerun (`app.py:84-91`); after "Revenir à Beni Mellal" the stale click may immediately override the reset. Needs a manual test.
10. **Convention drift ("UI text only via `TEXTS`")**: inline strings in `app.py` (`"Rotation"`, `"Total"`, `"Score"`, `"GWETTOP (surface)"`, `"T max"`, `"T moy."`, `"mm"`, `"/100"`); hardcoded constants inside templates that are not tied to code constants: "pluie < 1 mm/jour" (`explain.py:71`, vs `DRY_DAY_MM`) and "moins de 90 %" (`:110`, vs `MIN_COVERAGE`).
11. **Dependency risk** — `requirements.txt` floors are inaccurate: `st.plotly_chart(width="stretch")` / `st.dataframe(width="stretch")` work on 1.55.0 (checked) but I believe not on 1.35 (inferred); no upper bounds or lockfile; `numpy` not declared.
12. **Dead / unused**: `rank()["close_pairs"]` (computed, never displayed), five fetched/computed fields never used (§4), alfalfa and the perennial branches in water/climate scoring.
13. **Stale-data design**: the window is fixed to end 2025-12-31, so season 2026 is excluded; the cache never expires and does not record download date.
14. **Data labelling**: the UI/README state MERRA-2 ≈ 0.5° × 0.625° and CERES ≈ 1°, and the map draws a grid cell by rounding to those steps (`app.py:78-83`). I could not verify these resolutions or the cell alignment from the repo; they are hardcoded assertions.
15. **Season window vs crops** — durum wheat, chickpea and sugar beet harvest in May–July (`crops.json`) but only Oct–May is scored (inferred mismatch, see §5).

## 10. Security & Data-Integrity Notes

Flag only; nothing was changed.

- **Secrets:** none found. `.gitignore` excludes `data/cache/*` and `.streamlit/secrets.toml`. NASA POWER needs no key.
- **Input validation:** lat/lon from the map are not range- or region-checked. They only feed an HTTPS GET with fixed host and a cache filename built from rounded floats, so path traversal and injection risk is low. A user can request arbitrary global points (API load, off-region results scored with Tadla assumptions).
- **Outbound traffic:** `requests.get` to `power.larc.nasa.gov` with `timeout=90`; no response size limit (≈ 540 KB per point); no rate limiting on repeated clicks (each new 0.01° coordinate is a new 10-year call).
- **Silent substitution of data:** the fallback does show a warning banner, which is good. The weaker spots are: (a) the `cache` label has no date; (b) the fallback is cached in Streamlit memory (§9.2); (c) the generic `except Exception` labels any error, even a parsing bug, as "API indisponible".
- **Misleading-output risks for a judge:** (1) "Santé du sol" with no soil data (§9.1); (2) scores to one decimal with no numeric uncertainty; (3) the trend sentence (§9.7); (4) the soil-only total when NASA inputs are missing (§9.8). The French limitations tab and disclaimer do mitigate much of this, so the gap is mainly what the tab does not say.
- **Repo hygiene:** `.venv/` is untracked (good) but broken on this machine: `pyvenv.cfg` points to `C:\Python313\python.exe` and a build path under `C:\Users\user\Downloads\…`, so `.venv\Scripts\python.exe` does not run here. Re-create it rather than copying it. `.pytest_cache` is ignored.
- **Cache/fallback integrity:** nothing validates that a cached JSON matches its filename's coordinates/dates. (The local Beni Mellal cache file has the same byte size as the fallback, 539,218 bytes, but a different checksum, which I did not investigate; likely a separate download.)
